# Server-Side Credential Generation — Design & Implementation Plan

**Owner:** Aryan (backend + DB) · with Aman (server)
**Scope of this doc:** credential generation on the Express backend, storage in MongoDB, and delivery to the device.
**Out of scope (teammate):** on-device storage — encrypting the private key with an `id + PIN` combination, and using the credentials in NFC mutual auth.

> Resolves **Issue 9** — removes the hardcoded RSA keys in `CryptoUtils.kt` (both apps) and replaces them with per-user credentials issued at registration.

---

## 1. The problem today

Every device ships with the **same** hardcoded RSA keypair, baked into `CryptoUtils.kt`:

```
NursingDevice / Aggregator  -->  CryptoUtils.kt
                                  ├─ MY_PRIVATE_KEY_STR   = "MIIEvgIB..."  (same on every install)
                                  └─ OTHER_PUBLIC_KEY_STR = "MIIBIjAN..."  (same on every install)
```

Anyone who unpacks one APK owns the private key for *every* device. There is no per-user identity.

**Goal:** each user (nurse / patient device) gets a unique keypair + a certificate proving that keypair belongs to them, generated by the server at registration.

---

## 2. The credential model (from the design doc)

```
                    MongoDB Atlas (cloud)
                            │
                  ┌─────────┴──────────┐
                  │  Certifying        │
                  │  Authority (CA)    │   <- lives ON our Express backend
                  │  CA private key    │
                  │  CA certificate    │
                  └─────────┬──────────┘
                            │ signs
                            ▼
        ┌───────────────────────────────────────┐
        │   Per-user credential  (user U)        │
        │                                        │
        │   Kpri_U  = private key   ── to device │  (NEVER stored on server)
        │   Kpub_U  = public key    ── to Mongo  │
        │   Cert_U  = Kpub_U signed by CA key    │  (── to Mongo + device)
        └───────────────────────────────────────┘
```

A **certificate** = the user's public key, signed by the CA's private key. Anyone holding the CA's
*public* certificate can later verify that `Cert_U` is genuine — this is what eventually replaces the
hardcoded `OTHER_PUBLIC_KEY_STR` trust model.

**Locked design decisions:**

| Decision | Choice | Why |
|---|---|---|
| Where does the code live? | **`Nursing-Backend/`** (this repo) | Nurses, patients, records already live here. One server. |
| Is the private key stored in Mongo? | **No — public key + cert only** | A DB breach must not leak private keys. Private key is returned to the device once, then forgotten by the server. |
| Key algorithm | RSA-2048 | Matches `CryptoUtils.kt` (`RSA/ECB/PKCS1Padding`, `SHA256withRSA`). |

## 3. Target registration flow

```
   Device (nurse / patient)
          │
          │  POST /api/nurses/register   (or /api/patients/register)
          │  { deviceId, role, name, ...details }
          ▼
   ┌──────────────────────────────────────────────┐
   │  Express backend (Nursing-Backend)            │
   │                                               │
   │  1. Create user record (existing)             │
   │                                               │
   │  2. crypto.generateKeyPairSync('rsa',         │
   │            { modulusLength: 2048 })           │
   │            → Kpri_U , Kpub_U                   │
   │                                               │
   │  3. Cert_U = sign(Kpub_U) with CA private key │
   │                                               │
   │  4. Store in Mongo:                           │
   │     { deviceId, role, pubKey, certPem, ... }  │ ──► MongoDB Atlas
   │     (Kpri_U is NOT stored)                    │
   │                                               │
   └───────────────────────┬───────────────────────┘
                           │  5. Response
                           ▼
   {
     user:        { ... },
     credentials: {
        privateKey:    <Kpri_U>,    ◄── device stores this (teammate: encrypt w/ id+PIN)
        publicKey:     <Kpub_U>,
        certificate:   <Cert_U>,
        caCertificate: <CA cert>    ◄── device uses this to verify peers later
     }
   }
```

**Boundary:** everything inside the box is our job. Once the response leaves the server, the
teammate takes over (secure on-device storage of `privateKey`).

## 5. Step-by-step implementation

### Step 0 — Dependencies & config  🔲

```
npm install node-forge

.env       +  CA_KEY_PATH=./ca/ca-private-key.pem
              CA_CERT_PATH=./ca/ca-certificate.pem

.gitignore +  ca/
              .env
```

On Render, the CA private key must be provided as a **secret file / secret env var** — never committed.

---

### Step 1 — Bootstrap the CA (one time)  🔲

```
   node scripts/generateCA.js
          │
          ▼
   ┌───────────────────────────────────────────┐
   │  generateKeyPair (RSA-2048)                │
   │  build self-signed cert:                   │
   │     subject = issuer = "HealthSecure-CA"   │
   │     validity = 10 years                    │
   │     basicConstraints cA:true               │
   │     keyUsage: keyCertSign, cRLSign         │
   │  sign with its own private key             │
   └───────────────────┬───────────────────────┘
                       ▼
        ca/ca-private-key.pem   ◄── SECRET. never commit, never leave the server.
        ca/ca-certificate.pem   ◄── public. safe to ship to devices.
```

Run **once**. The guard refuses to overwrite an existing CA (regenerating it would invalidate every
certificate ever issued).

---

### Step 2 — Mongo schema: `models/Credential.js`  🔲

Replaces the placeholder `Certificate.js`. Generalized from patient-only to any device, **with no
private-key field by design**.

```
Credential {
   deviceId      : String   (required, unique, indexed)
   role          : String   (enum: 'nurse' | 'patient', required)
   userId        : String   (links to nurseId / patientId)
   pubKey        : String   (base64 SPKI DER)        ◄── public key only
   certPem       : String   (X.509 certificate, PEM)
   serialNumber  : String   (unique)
   issuedAt      : Date
   expiresAt     : Date
   isRevoked     : Boolean  (default false)
   revokedAt     : Date
}                            // timestamps: true

   ┌─────────────────────────────────────────────┐
   │  NOTE: there is deliberately NO privateKey   │
   │  field. If you ever see one here, that's a    │
   │  security bug.                                │
   └─────────────────────────────────────────────┘
```

### Step 3 — Credential service: `services/credentialService.js`  🔲

One reusable module so both register routes share exactly one code path.

```
   generateAndIssue(deviceId, role)
          │
          ▼
   ┌────────────────────────────────────────────────────────────┐
   │ 1. crypto.generateKeyPairSync('rsa',{modulusLength:2048})   │
   │        → privateKey, publicKey                              │
   │                                                            │
   │ 2. Export in the formats the DEVICE can parse:             │
   │    privB64 = privateKey.export(pkcs8, der) → base64        │
   │    pubB64  = publicKey .export(spki,  der) → base64        │
   │                                                            │
   │ 3. issueCertificate(publicKey, deviceId, role):            │
   │      build X.509  subject CN=deviceId, O=role              │
   │      issuer = CA   serial = random   validity = 1 year     │
   │      sign with CA private key (node-forge, SHA-256)        │
   │      → certPem                                             │
   └───────────────────────────┬────────────────────────────────┘
                               ▼
   returns { privB64, pubB64, certPem, serialNumber, issuedAt, expiresAt }
```

> **⚠️ Critical interop rule — key formats.**
> `CryptoUtils.kt` decodes keys with:
> - `PKCS8EncodedKeySpec` ← private key  → must be **base64 of PKCS#8 DER**
> - `X509EncodedKeySpec`  ← public key   → must be **base64 of SPKI DER**
>
> Return **base64-DER, not PEM** for the two keys. (The certificate is the exception — it's returned
> as PEM because the device parses it with a certificate factory, not a key spec.) If the teammate
> prefers PEM keys, they must strip the `-----BEGIN-----` header/footer before `Base64.decode`. **Agree
> on this in writing before integration.**

### Step 3a — Flowchart: how the backend generates the keys + cert  🔲

This is the heart of our work — the backend is the **only** place keys and certificates are born.
Read top to bottom; the dashed box is the CA stamp.

```
                 ┌──────────────────────────────────────┐
                 │  ON SERVER STARTUP (loaded once)      │
                 │  read ca/ca-private-key.pem  (secret) │
                 │  read ca/ca-certificate.pem  (public) │
                 └──────────────────┬───────────────────┘
                                    │  CA is ready, held in memory
                                    ▼
   ╔═══════════════════════════════════════════════════════════════════════╗
   ║  REQUEST ARRIVES:  register { deviceId:"nurse42", role:"nurse" }       ║
   ╚═══════════════════════════════════════╤═══════════════════════════════╝
                                           ▼
                  ┌────────────────────────────────────────┐
                  │  Already have a valid (non-revoked,     │
                  │  non-expired) credential for nurse42?   │
                  └───────────────┬──────────────┬─────────┘
                            YES   │              │  NO
                                  ▼              ▼
                    ┌──────────────────┐   ┌──────────────────────────────────┐
                    │ return PUBLIC    │   │  GENERATE KEY PAIR                │
                    │ material only    │   │  crypto.generateKeyPairSync(      │
                    │ (no private key; │   │     'rsa', {modulusLength:2048})  │
                    │  tell client to  │   │        │                          │
                    │  /rotate if lost)│   │        ├──►  Kpri  (private key)  │
                    └──────────────────┘   │        └──►  Kpub  (public key)   │
                                           └───────────────┬──────────────────┘
                                                           ▼
                          ┌────────────────────────────────────────────────┐
                          │  EXPORT in device-readable formats              │
                          │     privB64 = Kpri → PKCS#8 DER → base64        │
                          │     pubB64  = Kpub → SPKI   DER → base64        │
                          └───────────────────────┬────────────────────────┘
                                                  ▼
          ┌ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐
          │  BUILD THE CERTIFICATE (Cert_U)                                    │
          │    subject  = CN=nurse42, O=nurse                                  │
          │    publicKey= Kpub                  ◄── public key baked inside    │
          │    issuer   = HealthSecure-CA                                      │
          │    serial   = random unique number                                │
          │    validity = now  →  now + 1 year                                 │
          │                       │                                            │
          │                       ▼                                            │
          │    SIGN with CA PRIVATE KEY (SHA-256)  ◄── this is "CA-signed"     │
          │                       │                                            │
          │                       └──►  certPem  (the finished, stamped cert)  │
          └ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─┬─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘
                                              ▼
          ┌──────────────────────────────┐        ┌────────────────────────────┐
          │  SAVE TO MONGO (public only)  │        │  Kpri / privB64             │
          │    deviceId, role, userId     │        │  ─────────────────          │
          │    pubKey  = pubB64           │        │  NOT saved anywhere.        │
          │    certPem                    │        │  Lives only in this         │
          │    serialNumber, issuedAt,    │        │  function's memory, then    │
          │    expiresAt, isRevoked:false │        │  goes into the response and │
          └───────────────┬──────────────┘        │  is forgotten.              │
                          │                        └──────────────┬─────────────┘
                          └───────────────┬───────────────────────┘
                                          ▼
              ┌──────────────────────────────────────────────────────┐
              │  RESPOND to device:                                   │
              │  {                                                    │
              │    privateKey:    privB64,    ◄── secret, device keeps│
              │    publicKey:     pubB64,                             │
              │    certificate:   certPem,    ◄── Cert_U              │
              │    caCertificate: caCertPem   ◄── to verify peers     │
              │  }                                                    │
              └──────────────────────────────────────────────────────┘
```

**What never leaves the server:** the **CA private key** (used to sign, reused for everyone) and,
once the response is sent, **Kpri** (generated fresh per user, never written to disk or DB).

### Step 4 — Hook into registration  🔲

```
   POST /api/nurses/register            POST /api/patients/register
          │                                      │
          ▼                                      ▼
   ┌──────────────────────────────────────────────────────┐
   │  (existing) create / find user record                 │
   │                                                       │
   │  if no valid credential for deviceId:                 │
   │      { privB64, pubB64, certPem, ... }                │
   │          = credentialService.generateAndIssue(...)    │
   │                                                       │
   │      Credential.create({ deviceId, role, userId,     │
   │                          pubKey: pubB64, certPem,     │
   │                          serialNumber, issuedAt,      │
   │                          expiresAt })                 │
   │                                                       │
   │  respond { user, credentials:{ privateKey: privB64,  │
   │            publicKey: pubB64, certificate: certPem,   │
   │            caCertificate } }                          │
   └──────────────────────────────────────────────────────┘
```

**Idempotency (important):** the server does **not** keep the private key. So re-registering a
`deviceId` that already has a valid credential must **not** silently regenerate — that would orphan the
key already on the device.

```
   register(deviceId) ──► credential exists & not revoked & not expired?
                              │
                    ┌─────────┴───────────┐
                   YES                    NO
                    │                      │
          return PUBLIC material      generate new pair,
          only (no private key);      store, return full
          tell client to use          credentials
          /rotate if key is lost
```

### Step 5 — Credential management routes: `routes/credentials.js`  🔲

```
   GET  /api/credentials/:deviceId          → pubKey + certPem + status (NEVER private key)
   GET  /api/credentials/verify/:deviceId   → { valid, role } after expiry + revocation check
   POST /api/credentials/revoke             → mark isRevoked (lost-device flow)
   POST /api/credentials/rotate             → explicit re-issue, returns a fresh private key
```

Mount in `server.js`, replacing the old `/api/certificates` mount; update the boot log.

## 7. Security checklist

```
✔ Private key returned ONCE, over HTTPS only. Never logged. Never stored in Mongo.
✔ CA private key = crown jewel → secret file on Render, gitignored locally.
✔ Mongo breach leaks only public keys + certs (acceptable by design).
✔ Re-registration is idempotent (no silent key regeneration).
⚠ Device side must eventually VERIFY a peer's cert against caCertificate
   (current CryptoUtils.kt trusts a hardcoded public key and does NOT validate certs).
   Until that happens, the certificate is issued but not yet enforced — teammate's follow-up.
```
